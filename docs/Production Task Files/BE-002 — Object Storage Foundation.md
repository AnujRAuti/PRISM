- MinIO for local development.

# 3. STORAGE ARCHITECTURE

Implement this abstraction:

```text
Application
     ↓
StorageService
     ↓
S3-Compatible Interface
     ↓
┌───────────────┐
│ MinIO         │  Development
│ Amazon S3     │  Production
│ Other S3      │  Future
└───────────────┘
```

The application must NOT contain MinIO-specific logic throughout the codebase.

Only the storage implementation should know whether the backend is MinIO or AWS S3.

---

# 4. STORAGE CONFIGURATION

Use the existing application configuration system.

Do not create a second configuration system.

Configuration should support:

```text
S3_ENDPOINT
S3_ACCESS_KEY
S3_SECRET_KEY
S3_REGION
S3_BUCKET
S3_USE_SSL
```

If the existing configuration uses slightly different names, preserve the existing naming convention rather than unnecessarily renaming everything.

Requirements:

- Development points to MinIO.
- Production can point to AWS S3 or another S3-compatible provider.
- Credentials come from environment variables.
- No credentials are hardcoded.
- `.env` remains untracked.
- `.env.example` contains safe placeholders.

# 6. BUCKET ARCHITECTURE

Create a clear storage namespace.

At minimum:

```text
pofa-quarantine
pofa-evidence
```

Conceptually:

```text
UPLOAD
   ↓
QUARANTINE
   ↓
validation by BE-003
   ↓
TRUSTED EVIDENCE
```

BE-002 is responsible for providing the storage locations.

BE-002 must NOT implement the validation logic.

---

# 7. OBJECT KEY DESIGN

Do NOT use user-provided filenames as the authoritative object key.

Object keys should be generated by the backend.

Use a deterministic structure similar to:

```text
quarantine/{evidence_id}/original
```

and:

```text
evidence/{evidence_id}/original
```

Future derived artifacts can use:

```text
evidence/{evidence_id}/derived/{artifact}
```

Do not implement derived-artifact processing now.

The original object must be uniquely addressable.

---

# 8. STORAGE SERVICE INTERFACE

Create one clear storage abstraction.

It should provide operations such as:

```python
create_presigned_upload_url(...)
create_presigned_download_url(...)
object_exists(...)
get_object_metadata(...)
copy_object(...)
delete_object(...)
```

Add upload/download methods only if they are genuinely needed by the current backend architecture.

Keep the interface small.

Do not build a giant generic cloud abstraction.

---

# 9. PRESIGNED UPLOAD URL

Implement generation of a presigned upload URL.

Example conceptual flow:

```text
Backend
   ↓
StorageService
   ↓
presigned URL
   ↓
Client
   ↓
MinIO/S3
```

The backend should not need to proxy the entire file through FastAPI.

The actual evidence-upload endpoint comes in BE-003.

For now, implement and test the storage primitive only.

---

# 10. PRESIGNED DOWNLOAD URL

Implement a private-object download mechanism.

Example:

```text
Backend
   ↓
authorize access
   ↓
StorageService
   ↓
short-lived presigned URL
```

Objects must not be publicly readable by default.

Do NOT implement authentication/authorization in this milestone.

Just make the storage layer capable of private-object access.

---

# 11. OBJECT METADATA

The storage abstraction should be able to retrieve basic object metadata:

```text
object key
size
content type
ETag
last modified
```

Do not treat ETag as SHA-256.

Do not implement SHA-256 here.

SHA-256 belongs to BE-004.

---

# 12. OBJECT COPY / PROMOTION

The storage layer must support moving an object from quarantine to trusted storage.

Prefer a server-side copy operation:

```text
quarantine/{id}/original
          ↓
evidence/{id}/original
```

Then optionally delete the quarantine copy.

The exact promotion semantics should be documented.

Do NOT decide whether an evidence file is valid.

That is BE-003's responsibility.

---

# 13. STORAGE ERROR HANDLING

Create clear application-level storage errors.

Examples:

```text
StorageError
ObjectNotFoundError
BucketNotFoundError
PresignedUrlError
StorageConnectionError
```

Do not expose raw boto3/MinIO exceptions directly through API responses.

The storage implementation may internally catch provider-specific errors and translate them into application-level exceptions.

---

# 14. STORAGE RETRY BEHAVIOR

Do not create a complex distributed retry system.

For transient provider failures:

- [ ] Use reasonable SDK/network retry configuration.
- [ ] Avoid infinite retries.
- [ ] Return clear application errors.

Do not implement Redis retry queues yet.

---

# 15. BUCKET INITIALIZATION

Make development startup deterministic.

When Docker Compose starts:

```text
MinIO starts
    ↓
Buckets exist
```

A developer should not need to manually create buckets through the MinIO console.

Use a small initialization mechanism if required.

It must be:

- Idempotent.
- Safe to run repeatedly.
- Clearly documented.

Do not put application business logic in the initialization script.

---

# 16. STORAGE SECURITY

Implement sensible defaults:

- Buckets private.
- No anonymous read access.
- Credentials from environment.
- Presigned URLs expire.
- No arbitrary bucket selection from API input.
- No arbitrary object-key traversal.
- Backend controls object-key generation.

Do NOT implement authentication/RBAC yet.

---

# 17. OBJECT KEY SECURITY

Never allow an external caller to directly control an arbitrary storage path.

Reject or normalize unsafe values.

Do not allow keys such as:

```text
../../something
```

or:

```text
/etc/passwd
```

The application should generate storage keys from trusted identifiers.
