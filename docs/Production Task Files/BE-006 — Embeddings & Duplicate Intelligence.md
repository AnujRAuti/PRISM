# BE-006 — Embeddings & Duplicate Intelligence

## Objective

Build the first real duplicate-intelligence layer for Proof-of-Action.

BE-006 takes the existing evidence fingerprints and async analysis infrastructure and adds:

```text
SHA-256
   ↓
Exact duplicate detection

pHash
   ↓
Perceptual similarity

Embedding
   ↓
Semantic similarity

Candidate verification
   ↓
Stronger duplicate evidence
```

The system must **not** collapse these signals into a single "duplicate = true" decision.

Each signal must remain independently measurable and explainable.

# 1. Duplicate Intelligence Model

The system should treat duplicate detection as multiple independent signals.

```text
Evidence A
   │
   ├── SHA-256 ──────────────► exact byte identity
   │
   ├── pHash ────────────────► visual/perceptual similarity
   │
   ├── Embedding ────────────► semantic visual similarity
   │
   └── Local features ───────► geometric/content verification
```

These signals answer different questions.

### SHA-256

"Are these files byte-for-byte identical?"

### pHash

"Do these images have strongly similar visual structure?"

### Embedding

"Do these images represent visually/semantically similar content?"

### Local feature verification

"Do these candidate images contain corresponding local visual features?"

Do not represent these as equivalent measurements.

---

# 2. Exact Duplicate Detection

Use the existing persisted SHA-256 value.

For an evidence item:

```text
evidence.sha256
```

query other evidence records with the same SHA-256.

Do not recalculate hashes unnecessarily when the fingerprint already exists.

Expected behavior:

```text
SHA(A) == SHA(B)
        ↓
Exact duplicate candidate
```

SHA-256 equality is sufficient to establish byte-level equality.

Do not call it "same real-world photo" merely because the bytes match.

---

# 3. pHash Similarity

Use the real persisted pHash generated by BE-004.

pHash comparison should use actual Hamming distance.

Conceptually:

```text
distance = Hamming(hash_A, hash_B)
```

Lower distance means greater perceptual similarity.

Do not invent a similarity score.

If the system exposes a normalized similarity value, derive it deterministically from the actual hash distance and document the formula.

---

# 4. pHash Threshold

Do not blindly assume one universal threshold is scientifically correct.

Define the threshold as configuration.

Example:

```text
PHASH_MAX_HAMMING_DISTANCE
```

Use a documented default appropriate for the chosen hash implementation.

The threshold must be:

- explicit;
- configurable;
- deterministic;
- tested.

Do not tune the threshold simply to make test fixtures pass.

---

# 5. Embeddings

Implement a **real image embedding model**.

The embedding must be generated from the actual image.

Do not use:

```text
random vectors
zero vectors
hash-derived vectors
filename-derived vectors
metadata-derived vectors
hardcoded vectors
```

The model must produce a deterministic embedding for the same image under the same preprocessing/model configuration.

---

# 6. Model Choice

Use a practical pretrained image model suitable for local execution.

A CLIP-family model or equivalent pretrained vision-language/image embedding model is acceptable.

Examples include:

```text
CLIP
SigLIP
```

Choose one model that can realistically run in the project's development environment.

Do not introduce multiple embedding models in BE-006.

Document:

- model name;
- model version;
- embedding dimension;
- preprocessing;
- normalization behavior.

Do not claim that the embedding proves identity.

It only provides a similarity signal.

# 7. Model Loading

```text

```

Do not build a complicated model-serving system.

Do not add GPU orchestration.

Do not add distributed inference infrastructure.

# 10. Vector Persistence

Every successfully generated embedding must be persisted.

The stored vector must correspond to the actual image processed.

Do not store:

```text
None
[]
[0, 0, 0, ...]
random values
```

as a fake fallback.

If embedding generation fails:

```text
embedding_status = failed
```

or an equivalent explicit failure representation should be used.

Do not claim semantic similarity when no embedding exists.

---

At minimum, consider:

```text

embedding dimension

```

Do not overdesign this.

The purpose is reproducibility and future migration to another model.

If this metadata belongs in `AnalysisResult.result`, use that existing JSON structure rather than creating unnecessary tables.

# 12. Similarity Search

Implement actual vector similarity search through PostgreSQL/pgvector.

Do not:

```text

```

Use the database vector operator/index capabilities where practical.

The search should return candidate evidence IDs and actual similarity/distance values.

# 13. Vector Distance

Use the distance metric appropriate for the chosen embedding normalization.

For normalized CLIP/SigLIP-style embeddings, cosine similarity/distance is generally appropriate.

The implementation must use the actual database/vector operation.

Do not invent semantic scores.

If converting distance into similarity:

```text
similarity = deterministic transformation(distance)
```

Document the transformation.

# 15. Candidate Generation

Duplicate intelligence should generate candidates rather than immediately declaring fraud.

Example:

```text
Evidence A
   ↓
SHA exact matches
   +
pHash candidates
   +
Embedding candidates
   ↓
Candidate set
```

Candidate sources should remain distinguishable.

Example:

```json
{
  "candidate_id": "...",
  "signals": [
    "phash",
    "embedding"
  ]
}
```

Do not erase which signals generated the candidate.

---

# 16. Multi-Signal Candidate Verification

When multiple signals identify the same candidate:

```text
SHA
pHash
Embedding
Local features
```

record them independently.

For example:

```json
{
  "sha256_match": true,
  "phash_distance": 3,
  "embedding_similarity": 0.91,
  "local_feature_verified": true
}
```

The values must come from actual computations.

Do not combine them into a single fraud score.

Fusion belongs to BE-011.

---

# 17. Local Feature Verification

Implement local-feature verification only if it can be done cleanly within the current environment.

Use OpenCV SIFT or ORB.

Preferred flow:

```text
candidate generated
      ↓
local feature extraction
      ↓
feature matching
      ↓
geometric verification
      ↓
verified / not verified
```

This is stronger than merely comparing global image similarity.

If SIFT is unavailable in the installed OpenCV build, use ORB rather than fabricating verification.

If local-feature verification is implemented, record:

- method;
- keypoint counts;
- match count;
- verified match count;
- geometric verification outcome.

Do not convert this into a fraud determination.

---

# 18. Candidate Verification Boundaries

Local feature verification should run on **candidates**, not against every evidence item.

Do not create an O(N²) image-comparison system.

Example:

```text
100,000 evidence items

Embedding search
       ↓
Top K candidates

pHash filter
       ↓
small candidate set

Local features
       ↓
verification
```

The exact candidate count should be configurable.

# 19. DuplicateMatch

Reuse the existing `DuplicateMatch` table.

Current model:

```python
class DuplicateMatch(Base):
    __tablename__ = "duplicate_matches"

    id = Column(UUID(as_uuid=False), primary_key=True, default=gen_uuid)
    evidence_id = Column(
        UUID(as_uuid=False),
        ForeignKey("evidence.id"),
        nullable=False,
    )
    matched_evidence_id = Column(
        UUID(as_uuid=False),
        ForeignKey("evidence.id"),
        nullable=False,
    )
    similarity = Column(Integer)
    created_at = Column(
        DateTime(timezone=True),
        server_default=func.now(),
        nullable=False,
    )
```

Inspect the current model before changing it.

The existing integer `similarity` field may not be sufficient for the BE-006 signals.

If required, evolve it through a proper Alembic migration.

Prefer storing actual signal values separately rather than forcing unrelated measurements into one integer.

Possible fields:

```text
match_type
phash_distance
embedding_similarity
local_feature_match_count
local_feature_verified
```

Only add fields genuinely required by the implementation.

# 20. Match Direction

Avoid creating unnecessary duplicate rows for:

```text
A → B
B → A
```

where the relationship is logically symmetric.

Implement deterministic pair ordering or an appropriate unique constraint.

Example concept:

```text
min(evidence_id, matched_evidence_id)
max(evidence_id, matched_evidence_id)
```

Do not rely solely on application code if a database constraint can safely enforce uniqueness.

---

# 21. Idempotency

Running duplicate analysis on the same evidence multiple times must not create uncontrolled duplicate matches.

Expected:

```text
analysis run #1
    ↓
match A-B

analysis run #2
    ↓
same A-B relationship
    ↓
update/reuse existing match
```

Do not create another identical `DuplicateMatch` row every time the worker retries.

# 23. BE-005 Recovery Issue

Do **not** redesign the queue during BE-006.

The existing BE-005 processing-list approach has a future hardening concern:

```text

    ↓

    ↓
```

This is acknowledged technical debt.

Do not add a visibility-timeout/recovery subsystem unless it becomes strictly necessary for BE-006 correctness.

Record it for the later production/security hardening milestone.

BE-006 must continue using the existing queue abstraction.

# 26. Failure Handling

Embedding failure must not invalidate successful BE-004 fingerprinting.

Example:

```text
SHA-256      success
EXIF         success
pHash        success
Embedding    failed
```

This is a valid partial-analysis state.

Do not turn the entire job into fake success.

Likewise:

```text
Embedding    success
pHash        failed
```

must preserve the successful embedding.

Independent signals should remain independent.
