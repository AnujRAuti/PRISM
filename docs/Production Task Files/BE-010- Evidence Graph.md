BE-010 — Evidence Graph

Project: Proof-of-Action / Evidence Integrity & Intelligence Layer (EIIL)
Milestone: BE-010
Area: Backend — Evidence Graph
Branch: Backend
Status: Implementation Specification
Depends On: BE-001 → BE-009
Primary Goal: Establish the PostgreSQL-backed, provenance-aware Evidence Graph that represents relationships between existing PoA domain objects and analytical outputs.

1. Objective

Implement the first production version of the Evidence Graph for Proof-of-Action.

The Evidence Graph provides a structured representation of relationships between evidence, claims, activities, projects, analytical results, and other supported domain/intelligence objects.

The graph must:

use the existing PostgreSQL database;
preserve provenance;
support typed nodes and typed relationships;
support relationships generated by deterministic analysis;
support cross-project relationships subject to authorization boundaries;
preserve relationship history;
remain queryable through the existing FastAPI API;
integrate with BE-001 → BE-009 without breaking existing functionality.

The Evidence Graph is an intelligence representation layer.

It is not a truth engine.

A graph relationship must never automatically be interpreted as proof of fraud, authenticity, compliance, or wrongdoing.

2. Architectural Position

The Evidence Graph sits after the existing evidence/intelligence pipeline.

Evidence
   │
   ├── SHA-256
   ├── EXIF
   ├── pHash
   ├── Embedding
   ├── Duplicate Intelligence
   ├── Temporal Intelligence
   └── Vision Intelligence
          │
          ▼
   Evidence Graph
          │
          ├── Nodes
          ├── Relationships
          ├── Provenance
          └── Relationship history
          │
          ▼
   Future BE-011 Fusion

BE-010 must not implement BE-011.

The graph exists so later milestones can consume structured relationships rather than directly coupling themselves to every analytical subsystem.

PostGIS and pgvector remain available through the existing PostgreSQL architecture.

5. Supported Graph Node Types

BE-010 should support the following node types.

5.1 Domain nodes
PROJECT
ACTIVITY
CLAIM
EVIDENCE

These already exist in the backend.

The graph must reference them rather than duplicating their complete records.

5.2 Intelligence nodes

The graph may represent:

ANALYSIS_RESULT
VISION_DETECTION
DUPLICATE_MATCH

where useful for traceability.

However, do not duplicate large analytical payloads into the graph.

For example:

VisionDetection

remains the source of:

class name;
class ID;
confidence;
bounding box;
model;
configuration.

The graph relationship can reference the detection/result.

6. Node Representation

Create a graph node abstraction capable of identifying an existing object.

Minimum conceptual structure:

GraphNode
---------
id
node_type
entity_id
created_at

Where:

node_type = PROJECT | ACTIVITY | CLAIM | EVIDENCE | ...
entity_id = UUID of the underlying object

A graph node should not copy the underlying object's entire database row.

7. Node Identity

Node identity must be deterministic.

The combination:

node_type + entity_id

must uniquely identify the underlying graph node.

Example:

EVIDENCE + 8b4...
CLAIM    + 7a1...
PROJECT  + 2ce...

The same Evidence entity must never produce multiple graph nodes merely because different analyses ran against it.

9. Relationship Direction

Relationships are directional.

For example:

Evidence → Claim

must not automatically be treated as:

Claim → Evidence

unless the API explicitly provides the reverse traversal.

Direction must therefore be persisted.

Do not create dozens of speculative relationship types.

Every relationship type must have defined semantics.

11. Relationship Semantics
11.1 SUPPORTS

Represents an evidence-to-claim relationship where the evidence provides support for the claim.

It does not mean:

claim is true
11.2 CONTRADICTS

Represents an evidence-to-claim relationship where available evidence conflicts with the claim.

It does not mean:

fraud occurred
11.3 DUPLICATE_OF

Represents duplicate intelligence produced by BE-006.

It must preserve the underlying duplicate-analysis provenance.

The graph must not recalculate duplicate similarity.

11.4 TEMPORALLY_RELATED_TO

Represents a relationship established by temporal analysis.

It must not independently infer temporal relationships using new logic.

BE-008 remains the source of temporal intelligence.

11.5 HAS_DETECTION

Represents the relationship between an evidence/analysis entity and a vision detection.

The actual detection values remain in the BE-009 tables.

12. Provenance

Every derived graph relationship must be provenance-aware.

Minimum provenance information:

source
method
method_version
analysis_run_id
created_at

Where applicable.

Example:

source:
    vision_intelligence

method:
    yolo_detection

method_version:
    yolo11n / configured model version

analysis_run_id:
    <UUID>

For a human-created relationship, provenance should identify the actor/action where the existing architecture supports it.

13. Provenance ≠ Truth

This distinction is mandatory.

Provenance answers:

Where did this relationship come from?

It does not answer:

Is the relationship true?

Example:

Evidence A
    SUPPORTS
Claim B

with:

method = human_review

means the relationship was created/confirmed by a human review action.

It does not mean the claim has become universally true.

14. Relationship Status

Relationships need an explicit lifecycle/status.

Initial vocabulary:

ACTIVE
SUPERSEDED
INVALIDATED

Optional additional statuses may be introduced if required.

The implementation must not silently delete old analytical relationships merely because a newer analysis exists.

15. Relationship History

Derived relationships are historical records.

Suppose:

Analysis Run #1

creates:

Evidence A → DUPLICATE_OF → Evidence B

and later:

Analysis Run #2

does not establish that relationship.

Do not simply overwrite the first result.

The system must preserve analytical history and allow the current relationship state to be determined explicitly.

16. Idempotency

Repeated processing of the same analysis run must not create uncontrolled duplicate graph relationships.

The implementation should enforce appropriate uniqueness.

For example, a relationship generated by:

analysis_run_id
source
target
relationship_type

should be deterministic.

Do not globally enforce uniqueness that prevents legitimate historical relationships from different analysis runs.

18. Evidence ↔ Claim

Evidence-to-Claim relationships are a major purpose of BE-010.

The graph must support:

Evidence A → SUPPORTS → Claim X
Evidence B → CONTRADICTS → Claim X
Evidence C → ASSOCIATED_WITH → Claim X

Multiple evidence items may relate to the same claim.

One evidence item may relate to multiple claims.

Therefore:

Evidence ↔ Claim

is many-to-many.

Do not encode this as a single foreign key on either entity.

19. Activity ↔ Claim

The architecture defines:

Project
 ├── Activity
 └── Claim

with:

Claim ↔ Activity

as a many-to-many relationship.

BE-007 already contains project/activity/claim relationships.

BE-010 must represent them in the graph where appropriate without replacing the existing domain relationships.

20. Project Scope

Every graph query must be capable of respecting project scope.

Default behavior:

project-local

Cross-project traversal is explicitly supported but must not bypass authorization.

Example:

Project A
   │
 Evidence A
   │
 DUPLICATE_OF
   │
 Evidence B
   │
Project B

This relationship can exist.

However, BE-010 must not expose Project B's sensitive evidence merely because a graph edge exists.

Authorization becomes a formal concern in BE-015, but BE-010 must not design APIs that inherently assume unrestricted cross-project access.

21. Cross-Project Relationships

Cross-project relationships are intelligence signals.

They must not automatically:

merge projects;
merge evidence;
merge claims;
establish wrongdoing;
establish fraud;
establish authenticity.

They simply establish a graph relationship supported by a particular source/method.

33. Relationship Validation

Not every node combination is valid.

Examples:

EVIDENCE → SUPPORTS → CLAIM

may be valid.

But:

PROJECT → SUPPORTS → VISION_DETECTION

should not automatically be accepted.

Create a compatibility matrix.

At minimum validate the relationships introduced by BE-010.

Do not permit arbitrary node-to-node edges simply because both UUIDs exist.

38. No Explainability Engine

The graph may store a concise provenance/explanation string describing why a relationship was generated.

However, do not implement a dedicated explainability engine.

Example:

    duplicate_detection

    "Relationship generated by BE-006 duplicate analysis run."

That is sufficient for BE-010.

A full evidence explanation system is BE-012.

39. Analysis Run Provenance

Every automatically generated analytical graph relationship must be traceable to the analysis execution that generated it.

Example:

40. Reprocessing

If an analysis is rerun:

Analysis Run #1
Analysis Run #2

the graph must preserve the fact that two analytical executions occurred.

Do not mutate Run #1 into Run #2.

New analysis executions must be represented as new provenance.

41. Zero Observations

An analysis run that completes successfully with zero relationships/detections must remain:

COMPLETED

It must not become:

FAILED

and must not fabricate an empty relationship merely to make the graph non-empty.

42. Failed Analysis

If an analytical operation fails:

FAILED

must remain distinguishable from:

COMPLETED with zero observations

Do not create successful graph relationships from failed analysis runs.

43. Security Boundary

BE-010 must not implement full authentication/RBAC.

However, the design must remain compatible with BE-015.

Graph query interfaces must not be designed around the assumption that every caller can access every graph node.

Cross-project traversal must therefore be structured so authorization filtering can later be applied centrally.

The graph API returns relationships and references, not unrestricted underlying evidence.
