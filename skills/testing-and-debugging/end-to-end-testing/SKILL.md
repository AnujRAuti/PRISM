# End-to-End Testing

## 1. Purpose

Prove that the product works as a user experiences it: browser, API, database, and third parties together. E2E tests earn their cost only when they cover critical journeys and are stable; a flaky suite that everyone retries is worse than no suite. This skill covers journey selection, Playwright structure, locator strategy, test data isolation, authentication, waiting correctly, sharding, and failure artifacts.

**Scope:** your own environments with dedicated test tenants. E2E credentials are real credentials: scope them to test data, rotate them, and never commit them.

## 2. Activation Conditions

- Checkout, signup, login, payments, or any revenue-critical flow.
- Cross-service integration that unit/integration tests cannot cover.
- Regressions reaching users that lower layers missed.
- Existing E2E suite is slow, flaky, or disabled.
- Keywords: Playwright, Cypress, E2E, browser test, locator, getByRole, auto-waiting, trace viewer, fixtures, storageState, sharding, test data, visual assertions.

## 3. When Not to Use

- Field validation, formatting, or pure logic (unit or integration).
- Every permutation of a flow — test the journey, not the matrix.
- Visual appearance alone (use visual-regression-testing).

## 4. Required Context

1. Critical journeys ranked by business impact.
2. Environment: ephemeral preview, staging, or local compose stack.
3. Authentication mechanism and test account provisioning.
4. Data setup/teardown capabilities (API endpoints, seeds, DB access).
5. CI runtime budget and browser targets.

## 5. Operating Procedure

1. **Pick 5–15 journeys maximum**, each mapping to a business outcome ("customer completes checkout with a saved card").
2. **Structure with fixtures**: a `test` extended from the base that provides `page`, authenticated contexts, and API clients for setup.
3. **Locate by role and accessible name** (`getByRole`, `getByLabel`, `getByTestId` as a fallback). Never CSS classes, DOM depth, or text that marketing will rewrite.
4. **Set up data through the API**, not the UI; keep UI interactions for the behavior under test.
5. **Isolate per test**: unique tenant/user per test (generated by fixture), so tests can run in parallel and retries don't collide.
6. **Reuse authentication** via `storageState` produced once, rather than logging in through the UI in every test.
7. **Let Playwright auto-wait**; use web-first assertions (`expect(locator).toBeVisible()`) and never `waitForTimeout()`.
8. **Assert user-visible outcomes** (order confirmation, status badge) plus one backend check where correctness is invisible.
9. **Capture artifacts on failure**: trace, screenshot, video, console logs, network HAR.
10. **Shard and parallelize**; keep the suite under 15 minutes wall-clock in CI.
11. **Quarantine flaky tests** with an owner and an expiry, and fix the root cause (usually arbitrary waits or shared data).
12. **Run the same suite against preview deploys** for each PR when feasible, with seeded data.

## 6. Tools and Technologies

| Concern | Options |
|---|---|
| Runner | Playwright (`@playwright/test`) |
| Selectors | `getByRole`, `getByLabel`, `getByTestId` |
| Auth reuse | `storageState` with a setup project |
| Network control | `page.route`, HAR replay |
| Artifacts | `trace: "on-first-retry"`, `video: "retain-on-failure"` |
| Data | API clients in fixtures, factory endpoints, DB reset endpoint |
| CI | Sharding, `--reporter=blob` + `merge-reports`, GitHub Actions |
| Debug | `--ui`, `--debug`, Trace Viewer, `codegen` |

## 7. Practical Implementation

**Playwright config with projects, sharding, and artifacts:**

```ts
import {defineConfig, devices} from "@playwright/test";

export default defineConfig({
  testDir: "./e2e",
  fullyParallel: true,
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 2 : 0,          // retries only to surface flakes, not to hide them
  workers: process.env.CI ? 4 : undefined,
  timeout: 30_000,
  expect: {timeout: 7_000},
  reporter: process.env.CI
    ? [["blob"], ["github"], ["list"]]
    : [["html", {open: "never"}], ["list"]],
  use: {
    baseURL: process.env.BASE_URL ?? "http://localhost:3000",
    trace: "on-first-retry",
    video: "retain-on-failure",
    screenshot: "only-on-failure",
    testIdAttribute: "data-testid",
  },
  projects: [
    {name: "setup", testMatch: /auth\.setup\.ts/},
    {name: "chromium", use: {...devices["Desktop Chrome"], storageState: "e2e/.auth/user.json"},
     dependencies: ["setup"]},
    {name: "mobile", use: {...devices["Pixel 7"], storageState: "e2e/.auth/user.json"},
     dependencies: ["setup"]},
  ],
});
```

**Auth setup once, reused by every test:**

```ts
// e2e/auth.setup.ts
import {test as setup, expect} from "@playwright/test";
import fs from "node:fs";

const file = "e2e/.auth/user.json";

setup("authenticate", async ({page, request}) => {
  const email = `e2e+${Date.now()}@example.test`;
  const res = await request.post("/api/test/users", {
    data: {email, password: "Test-passw0rd-123", plan: "pro"},
  });
  expect(res.ok()).toBeTruthy();

  await page.goto("/login");
  await page.getByLabel("Email").fill(email);
  await page.getByLabel("Password").fill("Test-passw0rd-123");
  await page.getByRole("button", {name: "Sign in"}).click();
  await page.waitForURL("/dashboard");

  fs.mkdirSync("e2e/.auth", {recursive: true});
  await page.context().storageState({path: file});
});
```

**A journey test with data prepared via API:**

```ts
import {test, expect} from "@playwright/test";

test("customer checks out with a saved card and sees the receipt", async ({page, request}) => {
  const product = await (await request.post("/api/test/products", {
    data: {sku: `SKU-${Date.now()}`, name: "Trail Runner 42", priceCents: 849900, stock: 5},
  })).json();

  await page.goto(`/products/${product.id}`);
  await page.getByRole("button", {name: "Add to cart"}).click();
  await expect(page.getByRole("status")).toHaveText("Added to cart");

  await page.getByRole("link", {name: "Cart"}).click();
  await page.getByRole("button", {name: "Checkout"}).click();

  await page.getByLabel("Card number").fill("4242 4242 4242 4242");
  await page.getByLabel("Expiry").fill("12/30");
  await page.getByLabel("CVC").fill("123");
  await page.getByRole("button", {name: "Pay ₹8,499.00"}).click();

  await expect(page.getByRole("heading", {name: "Order confirmed"})).toBeVisible();
  const orderId = await page.getByTestId("order-id").textContent();

  const order = await (await request.get(`/api/test/orders/${orderId}`)).json();
  expect(order.status).toBe("paid");                 // backend truth, not just the UI
});
```

**Locator strategy, worst to best:**

```ts
// Do not use
page.locator("div.cart > div:nth-child(3) button");     // structure
page.locator(".btn-primary");                            // styling
page.locator("text=Submit");                             // any text node

// Prefer
page.getByRole("button", {name: "Submit order"});
page.getByLabel("Email address");
page.getByRole("row", {name: /INV-1001/}).getByRole("link", {name: "View"});
page.getByTestId("cart-total");                          // last resort, for values without semantics
```

**Network interception for third parties:**

```ts
test("shows a retry message when the card is declined", async ({page}) => {
  await page.route("https://api.payments.test/**", (route) =>
    route.fulfill({status: 402, contentType: "application/json",
                   body: JSON.stringify({error: {code: "card_declined"}})}));
  // ...complete checkout...
  await expect(page.getByRole("alert")).toContainText("Your card was declined");
});
```

**Waiting correctly:**

```ts
// Wrong: arbitrary sleep, flaky by design
await page.waitForTimeout(2000);

// Right: web-first assertion with a meaningful condition
await expect(page.getByRole("heading", {name: "Order confirmed"})).toBeVisible();

// Right: wait for a specific network response when the assertion depends on it
const paid = page.waitForResponse((r) => r.url().endsWith("/payments") && r.status() === 200);
await page.getByRole("button", {name: "Pay"}).click();
await paid;
```

**Accessibility check inside the journey:**

```ts
import AxeBuilder from "@axe-core/playwright";

test("checkout page has no critical accessibility violations", async ({page}) => {
  await page.goto("/checkout");
  const {violations} = await new AxeBuilder({page}).withTags(["wcag2a", "wcag2aa"]).analyze();
  expect(violations.filter((v) => v.impact === "critical")).toEqual([]);
});
```

**CI workflow with sharding and merged reports:**

```yaml
- run: npx playwright test --shard=${{ matrix.shard }}/4
  env: {BASE_URL: ${{ steps.deploy.outputs.preview_url }}}
- uses: actions/upload-artifact@v4
  if: always()
  with: {name: blob-report-${{ matrix.shard }}, path: blob-report/, retention-days: 7}
# merge job
- run: npx playwright merge-reports --reporter=html ./all-blob-reports
```

## 8. Quality Standards

- Only critical journeys are automated; each test maps to a business outcome.
- Locators use roles, labels, or test IDs; no CSS classes or DOM structure.
- No fixed sleeps; all waits are condition-based through web-first assertions.
- Test data is created per test through APIs with unique identifiers; teardown is automatic or unnecessary.
- Authentication is reused, not repeated through the UI in every test.
- Tests pass reliably (±0 flake over 50 consecutive runs) before being trusted as a gate.
- Artifacts (trace, video, screenshot) are uploaded on failure.
- Suite runtime stays inside the CI budget with sharding.

## 9. Verification and Testing

- Run the suite 20 times in a loop locally and in CI; flake rate must be zero.
- Force a failure and confirm the trace, video, and screenshot artifacts are produced and readable in Trace Viewer.
- Run with 4 shards in parallel; verify no test depends on another's data.
- Check that the suite fails when the feature is broken (deliberately revert a button handler).
- Verify tests pass with slow network throttling (`page.route` delay of 800 ms).

## 10. Security Considerations

- Test users must have minimum privileges and exist only in test environments; rotate credentials and never reuse production accounts.
- Do not record or store real card numbers; use provider test cards.
- Traces, videos, and HAR files capture credentials in headers and localStorage—treat artifacts as sensitive and set short retention.
- Never let E2E tests hit production payment gateways or send real emails/SMS; use sandbox modes or fakes.
- Ensure the test support endpoints (`/api/test/...`) exist only in non-production builds, or they become a data-injection backdoor.
- Scrub cookies and tokens from console logs when attaching to CI artifacts.

## 11. Failure Handling

- **Flaky timeouts:** arbitrary sleeps, animations, or a slow third party. Use assertions on state and mock the third party; disable animations in test builds.
- **Race on navigation:** the click navigates while the assertion runs — assert on the destination state, not on timing.
- **Tests interfere in parallel:** shared test users or unique-constraint collisions; generate per-worker data.
- **Auth setup fails intermittently:** rate limits on test-user creation; create users via a direct DB/API fixture instead of the login form repeatedly.
- **Suite is slow:** too many journeys or too many permutations; move detail assertions down to integration tests.
- **Artifacts missing:** check the `if: always()` on upload steps and that `trace` is enabled on retry.
